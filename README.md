# specgen — генератор интеграций с платёжными провайдерами

Инструмент на Ruby, который принимает OpenAPI-спецификацию платёжного
провайдера и собирает из неё готовую интеграцию для Space Payments: сервис по
контракту `Provider::BaseService`, документацию, фикстуры и отчёт о том, что в
спецификации неоднозначно.

Это компилятор, а не интеграция с одним провайдером. Спецификация превращается
в нейтральную модель провайдера, из модели по шаблонам собираются артефакты.
Всё, что выводится формально, выводится детерминированно по открытым
стандартам (ISO 4217, OpenAPI Overlay 1.0.0, JSON Schema, Standard Webhooks,
IETF Idempotency-Key). Всё, что формально не выводится, попадает в отчёт, а не
угадывается молча.

Хакатон Hack.Genesis 2026, кейс 1 (Space Payments).

## Быстрый старт

Нужны Ruby 3.2 или новее и Bundler.

```sh
git clone <repo-url> hackgenesis
cd hackgenesis
bundle install

# спецификация → четыре артефакта в output/
./integrate --spec spec/fixtures/specs/novapay.yaml --provider novapay --lang ruby
```

### Три команды, которые стоит запустить первыми

```sh
./integrate --all                                            # все десять спецификаций, сводная таблица
./integrate analyze --spec spec/fixtures/specs/novapay.yaml --explain
./integrate --spec spec/fixtures/specs/broken.yaml --provider broken
```

Первая — главный экспонат: одна команда, десять провайдеров, из них шесть
чужих настоящих.

Вторая печатает промежуточное представление, ничего не генерируя: провайдера и
серверы, авторизацию, каждую операцию с ролью и уверенностью, каждую схему с
полями и ограничениями, предупреждения. Рядом с каждым выведенным значением
стоит источник («задано явно», «по справочнику», «эвристика») и уверенность.
С `--explain` под каждым значением печатается обоснование, а под каждым
исправимым предупреждением — готовый фрагмент OpenAPI Overlay.

Третья — прогон на намеренно дырявой спецификации. Одиннадцать дыр
пронумерованы в шапке самого файла, и на каждую в `report.md` есть строка с
причиной и предложением. Генерация при этом не блокируется: четыре артефакта,
`ruby -c` и RuboCop чистые.

### Веб-интерфейс

```sh
cd space-payments-dashboard && pnpm install && pnpm build && cd ..
cp -r space-payments-dashboard/out/. public/
ruby bin/serve --port 9292      # http://localhost:9292
```

Тот же конвейер за экраном: загрузка спецификации, четыре артефакта с
отрендеренным Markdown, список предупреждений с готовыми фрагментами overlay,
сводная таблица по всем провайдерам. Один процесс отдаёт и API, и статику.
Сервер поднимается и без собранного фронта — тогда работает только API:

```
GET  /api/health   GET /api/specs   POST /api/analyze   POST /api/generate   GET /api/batch
```

### Докер

```sh
docker build -t specgen .
docker run --rm -p 9292:9292 specgen          # веб-интерфейс
docker run --rm specgen ./integrate --all     # CLI в том же образе
```

### Язык

Всё, что печатает инструмент, по умолчанию по-русски. Английский:

```sh
./integrate analyze --spec spec/fixtures/specs/novapay.yaml --locale en
SPECGEN_LOCALE=en ./integrate --help
```

Тексты лежат в `locales/<код>/`, по файлу на стадию; новый язык — новый
каталог, без правки кода. Справка `--help` читается при запуске класса,
поэтому следует переменной окружения, а не флагу.

В PowerShell вместо `./integrate` пишите `ruby integrate`. На Windows нужен
RubyInstaller **с DevKit (MSYS2)**: RuboCop тянет нативные расширения
(`prism`, `bigdecimal`), и без компилятора `bundle install` не пройдёт.

## Как это работает

```
 provider_api.yaml             overlay.yaml (необязательно)
        │                             │
        ▼                             ▼
 ┌─────────────┐    ┌────────────────┐
 │ SpecLoader  │───▶│ OverlayApplier │  читает YAML/JSON, разрешает $ref,
 └─────────────┘    └────────────────┘  применяет OpenAPI Overlay 1.0.0
                            │
                            ▼
                    ┌────────────────┐
                    │   Analyzers    │  независимые анализаторы: операции,
                    └────────────────┘  авторизация, схемы, статусы, ошибки,
                            │           вебхуки, единицы суммы, идемпотентность
                            ▼
                    ┌────────────────┐
                    │       IR       │  ProviderProfile: нейтральная модель
                    └────────────────┘  провайдера, каждое значение помечено
                            │           источником и уверенностью
                            ▼
                    ┌────────────────┐
                    │   Generators   │  ERB-шаблоны → service.rb,
                    └────────────────┘  INTEGRATION.md, fixtures.json
                            │
                            ▼
                    ┌────────────────┐
                    │    Reporter    │  report.md: предупреждения, покрытие,
                    └────────────────┘  готовые фрагменты overlay
```

Две точки входа — CLI и веб — зовут один и тот же конвейер.

| Стадия | Каталог | Что делает | Состояние |
|---|---|---|---|
| SpecLoader | `lib/specgen/spec_loader/` | YAML/JSON, версия OAS, `$ref`, циклы | готов |
| OverlayApplier | `lib/specgen/overlay/` | OpenAPI Overlay 1.0.0: `update` и `remove` по JSONPath | готов |
| Analyzers | `lib/specgen/analyzers/` | десять анализаторов, каждый заполняет свою часть IR | готов |
| Matchers | `lib/specgen/matchers/` | имя поля → роль: словарь, тип, ограничения, структура | готов |
| IR | `lib/specgen/ir/` | `ProviderProfile` и `Derived` (значение, источник, уверенность) | готов |
| Generators | `lib/specgen/generators/` | четыре артефакта из ERB-шаблонов `templates/` | готов |
| Reporter | `lib/specgen/reporter/` | экран `analyze` и `report.md` | готов |
| Web | `lib/specgen/web/` | Rack-API и раздача собранного фронта | готов |
| Validators | `lib/specgen/validators/` | сверка сформированных запросов со спецификацией | в работе |

Подробное состояние каждой стадии и способ её проверить одной командой —
`docs/STATUS.md`.

### Три уровня доверия

Для каждого элемента спецификации идём по цепочке и останавливаемся на
первом успехе:

1. **Формальная структура спеки** (`required`, `enum`, `pattern`, `minimum`,
   `format`, `$ref`, `securitySchemes`, `dependentRequired`) — используем молча.
2. **Справочники и структурные эвристики** (ISO 4217, словари синонимов,
   роли эндпоинтов по методу, пути и тегу) — используем, помечаем источник и
   уверенность.
3. **Не вывелось или низкая уверенность** — берём лучшего кандидата, но
   помечаем: предупреждение в `report.md`, `TODO` в сгенерированном коде со
   списком кандидатов и баллами, готовый слот в overlay-файле.

Грех не догадка, а догадка без пометки. Молчаливая ошибка в платёжной
интеграции дороже одного ручного шага: неверно выведенный множитель суммы
означает перевод в сто раз больше, а код при этом выглядит корректным.

Есть ровно одно место, где инструмент осознанно **не** берёт лучшего
кандидата. Статус `PART_DONE` из примера уведомления читается как `DONE`, то
есть «выплачено», если снять ведущее слово. Частично проведённый платёж,
помеченный как выплаченный, — запрещённое направление ошибки, поэтому вывода
нет вовсе, а предупреждение называет отвергнутого кандидата и объясняет отказ.

### Роли вместо имён полей

Имён полей бесконечно много (`amount`, `sum`, `total`, `value`), ролей в
платёжной области шестнадцать. Ядро работает с ролями, сопоставление
«имя → роль» делает слой матчеров по принципу composite matcher (COMA, Rahm &
Bernstein 2001): четыре независимых матчера голосуют, решение и арифметика
голосов попадают в отчёт.

Инвариант: в `lib/` нет ни одной провайдер-специфичной строки. Проверяется
командой и в CI:

```sh
grep -rinE 'novapay|\bsbp\b' lib/     # пусто
```

## Как добавить нового провайдера

Строками в справочниках, а не кодом. Пример: провайдер называет статус
`sending`, которого у нас не было.

```sh
./integrate --spec new_provider.yaml --provider acme
# report.md: «статус sending не найден ни в каноне, ни среди синонимов
#             rules/statuses.yml; выберите внутренний статус в overlay или
#             добавьте синоним в справочник»
```

Одна строка в `rules/statuses.yml`:

```yaml
synonyms:
  in_progress:
    - sending
```

и повторный прогон читает статус молча. Так же добавляются имена полей
(`rules/roles.yml`), лексика операций (`rules/operations.yml`), политика
обработки кодов ошибок (`rules/errors.yml`), профили подписи вебхуков
(`rules/signatures.yml`), алиасы заголовка идемпотентности.

Второй путь — не трогая репозиторий вообще: `report.md` печатает готовые
фрагменты OpenAPI Overlay 1.0.0, их надо склеить в файл и передать флагом.

```sh
./integrate --spec new_provider.yaml --overlay acme.yaml
```

На выданной спеке это видно так: условная обязательность `bank_code`,
высказанная в спецификации прозой, читается эвристикой с уверенностью 0.50 и
даёт предупреждение. Фрагмент из отчёта, положенный в overlay, превращает её в
`dependentRequired` с уверенностью 1.00 — предупреждений становится 16 вместо
18, а в сгенерированном коде меняется комментарий над полем. Отчёт и overlay —
один механизм, а не две несвязанные возможности.

## Структура репозитория

```
integrate                     запуск из корня (./integrate ...)
bin/integrate                 исполняемый файл CLI
bin/serve                     HTTP-сервер веб-интерфейса
bin/ruby-share                доля Ruby по правилам GitHub Linguist
bin/fetch-real-specs          загрузка чужих публичных спецификаций в tmp/

templates/                    ERB-шаблоны артефактов
rules/                        справочники: роли, статусы, ISO 4217, подписи, контракт
locales/<код>/                тексты для человека, по файлу на стадию
spec/unit/                    RSpec ядра
spec/golden/                  доказательство побайтовой повторяемости вывода
spec/fixtures/specs/          десять спецификаций: выданная, три свои, шесть чужих настоящих
spec/fixtures/overlays/       примеры OpenAPI Overlay
space-payments-dashboard/     веб-интерфейс: Next.js, собирается в статику
config.ru                     точка входа Rack
docs/                         концепция, разбалловка, допущения, вопросы экспертам
output/                       результат генерации, в репозиторий не попадает
```

## Команды и флаги

| Команда / флаг | Назначение |
|---|---|
| `generate` | генерация артефактов, команда по умолчанию |
| `analyze` | разбор без генерации: что инструмент понял в спецификации |
| `--spec FILE` | путь к OpenAPI-спецификации (YAML или JSON) |
| `--provider NAME` | имя провайдера; по умолчанию выводится из `info.title` |
| `--lang ruby` | целевой язык, поддерживается только `ruby` |
| `--overlay FILE` | OpenAPI Overlay 1.0.0 с ручными переопределениями |
| `--output DIR` | каталог результата, по умолчанию `output/` |
| `--all` | прогнать все спеки из каталога и напечатать сводку |
| `--specs DIR` | каталог для `--all`, по умолчанию `spec/fixtures/specs` |
| `--explain` | у `analyze`: обоснование под каждым выведенным значением |
| `--locale ru\|en` | язык вывода |
| `--strict` | завершиться с кодом 1, если в отчёте есть предупреждения |
| `version` | версия генератора |

Коды возврата: `0` успех, `1` ошибка генерации или предупреждения при
`--strict`, `2` неверное использование.

## Разработка

```sh
bundle exec rspec       # 928 примеров
bundle exec rubocop     # 290 файлов; тот же конфиг применяется к сгенерированному коду
ruby bin/ruby-share     # доля Ruby: 94.6 % (с ERB 96.1 %)
```

CI (GitHub Actions) на Ruby 3.2 и 3.4 прогоняет то же самое плюс всё
остальное из Definition of done: пакетный прогон по десяти спецификациям,
`ruby -c` и RuboCop на каждом сгенерированном сервисе, разбор каждого
`fixtures.json`, повторный прогон с `diff -r` для доказательства
детерминированности и проверку провайдер-нейтральности `lib/`.

## Честные ограничения

- **Мок-провайдер не сделан.** Эксперты кейса сказали, что оценивают
  сгенерированный класс, а живой трафик не требуется, поэтому он остался в
  бонусах.
- **`--fix`** (собрать overlay из фрагментов отчёта автоматически) не
  реализован: фрагменты печатаются готовыми, но склеивает их пока человек.
- **Докер не проверен сборкой** на машине разработки: демон недоступен.
  `Dockerfile` написан и обоснован построчно, но первый запуск обязателен.
- **Покрытие на чужих спецификациях 23–59 %** — и это честная цифра, а не
  подкрученная. Рядом с ней отчёт печатает вторую, «в границах контракта»
  (46–92 %): у неё из знаменателя вычтено то, чему четыре метода
  `Provider::BaseService` не могут дать места — адрес держателя счёта
  положить некуда ни в запрос, ни в разбор ответа. Первая отвечает «сколько
  спецификации задействовано», вторая — «сколько упущено из того, что вообще
  можно было взять». Вычтенное не спрятано: каждый вид назван в разделе 2
  `report.md` со своей причиной.
- **Заголовки разделов `report.md` остаются русскими** при `--locale en`: они
  лежат прозой в шаблоне.

## Правила хакатона

| Требование | Как соблюдаем |
|---|---|
| Без нейросетей в прототипе | только справочники, регулярные выражения, строковые метрики, эвристики по структуре; ни одного сетевого вызова в рантайме |
| Ruby больше 50% кода | 94.6 % по правилам GitHub Linguist, проверяется `bin/ruby-share`; фронт — оболочка, вся логика в Ruby |
| Только открытый код | все зависимости с открытыми лицензиями, список в [DEPENDENCIES.md](DEPENDENCIES.md) |
| Без секретов | сгенерированный код читает ключи из `provider.credentials` или `ENV.fetch`, в фикстурах только заглушки, номера карт только тестовые |
