# Что осталось: промпты для новых сессий

Составлено 5 сентября 2026, после второго чекпоинта. Каждый блок ниже —
готовый промпт: копировать целиком в новую сессию и отправлять как есть.
Промпты самодостаточны, потому что новая сессия не помнит предыдущую: в
каждом сказано, что прочитать, каким агентом работать и чем закончить.

Порядок — по отдаче за час работы. Первые три успеть до третьего чекпоинта,
остальные — по остатку времени до стоп-кода.

Правила, общие для всех:

- запускать по одному промпту за раз. Второй и третий меняют то, что
  попадает в `output/`, и одновременный прогон разойдётся на golden-тестах;
- в конце каждой сессии обязателен «Definition of done» из `CLAUDE.md`:
  `bundle exec rspec`, `bundle exec rubocop`, прогон `./integrate`,
  `ruby -c` на сгенерированном файле, golden-тест, `grep` по `lib/` на
  провайдер-специфичные строки;
- в Git Bash перед командами: `export PATH="/c/Ruby34-x64/bin:$PATH"`;
- ответы экспертов приходят в общий чат: когда придут, они закрывают
  вопросы 1, 2 и 4 из `docs/checkpoint-2/questions-to-chat.md`, и это
  отдельная маленькая правка справочников, а не работа для этих промптов.

## 1. Свои альтернативные спецификации

Зачем: критерий E4.1 (7 баллов) — «решение работает со спецификациями,
отличающимися набором методов, полей и параметров». Чужие настоящие спеки у
нас уже есть, а своих управляемых — нет, и на `broken.yaml` держится весь
рассказ про то, что инструмент находит дыры и всё равно генерирует.

```
Прочитай CLAUDE.md и docs/STATUS.md целиком, затем docs/PROMPTS.md, промпт 10.

Используй агента rules-curator. Напиши три спецификации в
spec/fixtures/specs/:

- cardpay.yaml: выплата на карту вместо СБП, авторизация Bearer, статусы
  succeeded/declined/queued, суммы в центах и USD, вебхук по Standard
  Webhooks (webhook-id / webhook-timestamp / webhook-signature),
  идемпотентность через X-Request-Id;
- depositbank.yaml: депозиты вместо выплат, major units через type: number,
  JPY с нулевой экспонентой ISO 4217, вебхуков нет — статус только
  поллингом, OpenAPI 3.1 с настоящим dependentRequired, OAuth2 client
  credentials;
- broken.yaml: намеренные дыры — нет examples, нет operationId, незнакомое
  обязательное поле, противоречие между enum статусов и примерами, ответ без
  объявленной схемы, поле суммы без указания единиц.

Каждая — пять-семь операций, реалистичные схемы, заполненные examples там,
где они по замыслу есть. Ни одна не должна быть переименованным NovaPay:
другие имена полей, другие статусы, другая структура получателя.

Затем прогони по каждой ./integrate --spec ... и ./integrate --all, и
доведи до того, чтобы:
- ни одна не падала со стектрейсом;
- broken.yaml давала осмысленный report.md: каждая дыра — строка с причиной
  и предложением, генерация при этом не блокировалась;
- всё, что инструмент не распознал в новых спеках, лечилось строками в
  rules/, а не ветками в lib/.

В конце добавь цифры по новым спекам в docs/STATUS.md и проверь Definition
of done из CLAUDE.md целиком.
```

## 2. OverlayApplier: флаг `--overlay` должен работать

Зачем: сейчас `./integrate --spec ... --overlay file.yaml` печатает
«overlay игнорируется» — флаг есть, поведения нет. При этом overlay заявлен в
`CLAUDE.md` как наш механизм переопределений, `report.md` уже печатает
готовые фрагменты, а анализаторы читают расширения `x-specgen-*`. Не хватает
одного звена: применить внешний файл к документу до анализа. Это критерий
E4.3 и заодно единственная дыра в конвейере, которую видно из справки.

```
Прочитай CLAUDE.md (раздел про OpenAPI Overlay 1.0.0) и docs/STATUS.md,
затем docs/IR.md — таблицу расширений x-specgen-*.

Используй агента ir-architect для проектирования, дальше пиши сам.

Реализуй стадию OverlayApplier между SpecLoader и анализаторами:

- формат — OpenAPI Overlay Specification 1.0.0: overlay, info, actions[],
  у действия target (JSONPath) и update или remove;
- применяется к разобранному документу до разрешения $ref, результат идёт
  дальше по конвейеру без изменений в анализаторах;
- поддержи подмножество JSONPath, которое реально печатает наш же report.md:
  $.components.schemas.X, $.components.schemas.X.properties.Y,
  $.paths['/p'].post и обращение по индексу массива;
- target, который ничего не нашёл, — понятная ошибка с файлом и путём, а не
  тихий пропуск: молчаливо проигнорированный overlay хуже отсутствующего;
- в report.md добавь строку о том, какие действия overlay применились: то,
  что переопределено человеком, обязано быть видно.

Ошибки — свои классы от SpecGen::Error, сообщения через Texts в обеих
локалях. Тесты: применение update и remove, несуществующий target, битый
overlay, полный цикл «прогон → фрагмент из report.md → overlay → повторный
прогон, предупреждение исчезло».

Проверь Definition of done из CLAUDE.md целиком и обнови docs/STATUS.md:
строка OverlayApplier в таблице стадий должна перестать быть «не начат».
```

## 3. Вторая цифра покрытия

Зачем: на чужих спеках покрытие 23–39 %, и цифра выглядит слабее, чем есть.
Часть непокрытого непокрываема по построению: контракт `BaseService` читает
из ответа четыре роли, а в спеке Adyen триста полей. Честный ответ — не
подкручивать число, а показать два: сколько взято от всей спецификации и
сколько от того, что контракт вообще может использовать.

```
Прочитай CLAUDE.md и docs/STATUS.md, затем
lib/specgen/generators/report/coverage.rb и coverage_fields.rb.

Используй агента codegen-engineer.

Добавь в раздел 2 report.md вторую цифру: «в границах контракта». В её
знаменатель не входят элементы, которые методам Provider::BaseService не
нужны по построению:

- поля тел ответов, чья роль не входит в четыре читаемые сервисом;
- необязательные поля тел запросов без роли (CLAUDE.md, «Что генерируем при
  неполной спеке»: они намеренно не идут в payload);
- операции, роль которых не отображается на контракт и не получает
  отдельного метода.

Обе цифры печатаются рядом с одним абзацем объяснения, обе попадают в
метрики артефакта (Artifact#metrics) и в сводку пакетного прогона
./integrate --all отдельной колонкой. Никакого «среднего по измерениям»:
формула остаётся долей элементов, меняется только знаменатель второй цифры.

Тексты — через Texts в обеих локалях. Тесты: обе цифры на novapay.yaml, на
спеке без вебхуков и на спеке, где все элементы вне контракта. Обнови
golden-эталон (SPECGEN_UPDATE_GOLDEN=1) и цифры в docs/STATUS.md.

Проверь Definition of done из CLAUDE.md целиком.
```

## 4. README, инструкция запуска и сценарий третьего чекпоинта

Зачем: у технического жюри «инструкция по запуску и настройке» — 3 балла, у
экспертов «понятный способ запуска» — часть E5. README писался до пакетного
прогона и до изменений контракта, поэтому местами устарел. Плюс на третьем
чекпоинте показываем живой терминал: эксперт заметил, что во второй раз всё
было завёрнуто в презентацию.

```
Прочитай CLAUDE.md, docs/STATUS.md, docs/CHECKPOINT-2.md (раздел 0 — итоги
встречи) и README.md.

Приведи README в соответствие с тем, что есть сейчас:
- установка на чистой машине: Ruby 3.2+, bundle install, ./integrate --help;
- три команды, которые стоит запустить первыми: analyze, generate, --all;
- что появляется в output/ и как это проверить (ruby -c, rubocop с
  config/rubocop_generated.yml, JSON.parse);
- как добавить нового провайдера: строки в rules/, а не код, с примером;
- ограничения, честно: overlay, мок-провайдер, веб-интерфейс — их состояние.

Затем напиши docs/CHECKPOINT-3.md по образцу docs/CHECKPOINT-2.md:
тайминг на 8 минут, команды для прогона до встречи, что показывать на
экране в каком порядке, что делать, если упало, таблица «где мы по баллам»
и список вопросов экспертам. Главное отличие от прошлого раза: показываем
живой терминал, а не вывод в слайде, и начинаем с пакетного прогона по
чужим спекам — именно его просили эксперты.

Ничего не выдумывай: все числа бери прогоном, а не из docs/, они могли
устареть.
```

## 5. Сверка сформированных запросов со спецификацией

Зачем: критерий E2.1 «сервис формирует и отправляет запросы» — эксперты
сказали, что живой трафик не нужен, оценивают сгенерированный класс. Тогда
единственный способ доказать правильность запроса — проверить его против
самой спецификации. Это остаток промпта 9 из `docs/PROMPTS.md`.

```
Прочитай CLAUDE.md, docs/STATUS.md и docs/PROMPTS.md, промпт 9.

Используй агента test-engineer.

Добавь стадию проверки: тело запроса, которое собирает сгенерированный
сервис, валидируется против схемы запроса из спецификации, а тела фикстур —
против схем ответов. Гем брать открытый и на Ruby (committee или
openapi_first), записать в DEPENDENCIES.md с лицензией.

Проверка идёт по фикстурам из fixtures.json: каждый запрос обязан проходить
схему операции, каждый ответ — схему своего кода. Несоответствие — понятная
строка с путём поля, а не исключение гема наружу.

Результат — тесты на генератор (не на сгенерированный сервис: эксперты
сказали, что тесты нужны на наше решение), плюс строка в report.md о том,
что запросы сверены со спецификацией и сколько проверок прошло.

Проверь Definition of done из CLAUDE.md целиком.
```

## Чего в этом списке нет и почему

- **`--fix` и цикл с overlay** (`docs/PROMPTS.md`, промпт 11) — эксперты
  прямо сказали, что чужие спецификации важнее. После пункта 2 механизм
  будет готов, и `--fix` станет получасовой надстройкой; раньше — нет.
- **Новые роли полей** (`account_number`, `iban`, `recipient_name`) — они
  подняли бы покрытие полей тел запросов, но каждой нужно выражение
  платформы в `rules/contract.yml`, а какие поля есть у `operation` — это
  вопрос 1, заданный экспертам 5 сентября. Пока ответа нет, это была бы
  догадка о платформе, а не о спецификации.
- **Режим сравнения версий спеки** (промпт 13) — красиво, но ни в одном
  критерии не оценивается.
