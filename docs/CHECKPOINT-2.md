# Чекпоинт 2 — итоги встречи

Дата: 5 сентября 2026. Формат: восемь минут, четыре на показ и четыре на
вопросы. Слайды — `docs/checkpoint-2/checkpoint-2.pdf`.

## Что показали

Полный проход: одна команда, четыре артефакта по выданной спецификации;
сгенерированный сервис (`STATUS_MAP`, `ERROR_MAP`, `check_conditions`, ветка
дедупликации на 409, `process_callback` с проверкой подписи, UUID v5 для
ключа идемпотентности, `cancel` и `balance` отдельными методами);
`INTEGRATION.md` с разделом принятых допущений; `fixtures.json` с настоящей
подписью; `report.md` с покрытием и готовым фрагментом Overlay; прогон на
чужой спецификации Adyen Transfers.

Показ был свёрнут в презентацию с выводом команд. Эксперт спросил: «Окей,
то есть вы это всё завернули в презентацию?» — и на третьей встрече
показывали живой терминал.

## Что сказали эксперты

Дословно — `docs/QUESTIONS.md`, вопросы 1, 3, 6, 7, 13–17; письменные
ответы в чате в тот же день — вопросы 18–25. Что изменилось в коде:

| Ответ | Что поменяли |
|---|---|
| Идентификатор провайдера сохраняет платформа вне сервиса; `create_request` возвращает `success(result: { id: … })` | Из сгенерированного кода убраны `operation.update` и `Operation.find_by`; `create_request` отдаёт идентификатор в `result` |
| `process_callback` получает уже разобранный JSON | Колбэк не разбирает тело; подпись проверяет публичный `verify_webhook_signature(raw_body, headers)` для маршрута вебхука |
| Канон статусов и ошибок — таблицы из описания кейса | 402 и `insufficient_balance` → `retry_backoff`; `cancelled` → `rejected` подтверждён |
| Конфиг шлюза платформе не нужен; адрес и авторизация берутся из спецификации | Раздел 6 `INTEGRATION.md` стал сводкой параметров подключения |
| У операции гарантированы `id`, `amount`, `payout_requisite` (JSONB-хеш); плоских реквизитов нет | Реквизиты читаются из `payout_requisite`: у СБП вложенный хеш, у карты плоский ключ |
| Первый аргумент `failure` — код платформы в духе HTTP | Коды вынесены в `failure_codes` в `rules/contract.yml` |
| `request_method` — логический метод шлюза; при нескольких способах выплаты — ветки в одном сервисе | Условная обязательность стала веткой `case request_method` |
| `amount_limit_exceeded` — лимит одной выплаты, отклонять | Правило `operation_limit` → `reject`, квоты → `escalate` |
| Реквизит, которого нет в схеме платформы, вслепую не генерировать | TODO и строка «куда мапить» в `INTEGRATION.md` |
| Важнее уметь разбирать чужие OpenAPI, чем цикл overlay | Приоритет — чужие спецификации; `--fix` доделан позже |

Просьба, которую выполнили: прислать через куратора репозиторий и
сгенерированный сервис по чужой спецификации — «было бы интересно на этот
файлик посмотреть».
