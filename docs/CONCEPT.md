# Концепция решения

Документ для команды и для защиты. Здесь зафиксировано, почему решение
устроено именно так и на какие стандарты опирается каждое решение.

## Идея

Мы делаем не парсер одной спеки, а компилятор: спецификация провайдера
превращается в промежуточную модель, из модели по шаблонам собираются
артефакты. Всё, что можно вывести формально — выводим детерминированно по
стандартам и справочникам. Всё, что формально не выводится — не угадываем
молча, а выносим в отчёт и в стандартный файл переопределений.

## Три уровня доверия

Для каждого элемента спеки идём по цепочке и останавливаемся на первом успехе.

| Уровень | Источник | Поведение |
|---|---|---|
| 1 | Формальная структура спеки: `required`, `enum`, `pattern`, `minimum`, `format`, `$ref`, `operationId`, `securitySchemes` | Используем молча |
| 2 | Справочники и структурные эвристики: ISO 4217, словари синонимов, роли эндпоинтов | Используем, помечаем происхождение и уверенность |
| 3 | Не вывелось или низкая уверенность | Warning в отчёт, TODO в коде, слот в overlay |

Позиция, согласованная с экспертами кейса: из структуры — автоматически,
неоднозначное из `description` — TODO и warning плюс опциональный общий
overrides-файл. Эвристики допустимы как best-effort, но молча угадывать
критичное хуже.

Обоснование: молчаливая ошибка в платёжной интеграции дороже одного ручного
шага. Неверно определённый множитель суммы означает перевод в сто раз больше
или меньше, и код при этом выглядит корректным.

## Конвейер

```
SpecLoader → OverlayApplier → Analyzers → IR → Generators → Validators → Reporter
```

Ключевое решение — промежуточное представление. Ядро не генерирует Ruby
напрямую из YAML, а сначала строит нейтральное описание провайдера. Добавить
провайдера означает дописать строки в справочники, а не править код.

Это не наше изобретение. Официальная документация openapi-generator описывает
ту же схему: генератор строит структуру данных из документа OpenAPI, спеки
версий 2.0 и 3.x нормализуются в одну модель, и затем модель применяется к
шаблонам.

Инвариант: в `lib/` нет провайдер-специфичных строк. Всё специфичное живёт в
`rules/` (данные) и в overlay-файлах.

## Роли вместо имён полей

Имён полей бесконечно много (`amount`, `sum`, `total`, `value`), а ролей в
платёжной области около пятнадцати. Ядро работает с ролями.

Сопоставление «имя → роль» делает слой матчеров, построенный по принципу
composite matcher: независимые матчеры (по имени, типу, ограничениям,
структуре) с весами и агрегацией, порог уверенности, ниже порога — warning.

Академическая база — schema matching, область с историей более двадцати лет.
Cupid комбинировал лингвистическое и структурное сходство, COMA повышала
точность за счёт интеграции результатов нескольких матчеров через
мета-матчинг, Similarity Flooding работала через вычисление неподвижной точки
на графе. Схемные методы используют метаданные: имена атрибутов, типы,
ограничения.

Важное практическое следствие из литературы: строковые метрики не связывают
семантически разные имена (канонический пример — `Ship` и `Deliver`), поэтому
словарь синонимов не костыль, а обязательный отдельный матчер. И ещё одно:
человек, проверяющий результат, — штатная часть архитектуры COMA, а не признак
слабости решения.

Всё это старше нейросетей на два десятилетия, что снимает вопрос о запрете
п. 7.8.4 Положения.

## Стандарты, заменяющие догадки

### ISO 4217 — единицы суммы

Проблема: в спеке единицы описаны прозой («Сумма в копейках»).

Решение: стандарт задаёт для каждой валюты экспоненту минорной единицы —
сколько десятичных знаков валюта использует. RUB 2, USD 2, JPY 0, KWD 3,
CLF 4. Читаем код валюты из `currency`, смотрим в вшитую таблицу, получаем
множитель. Текст описания не участвует.

Так работает вся индустрия: платёжные API принимают суммы в минорных единицах
по ISO 4217 — для EUR и USD центы, для JPY целые единицы без десятичных
знаков, для KWD тысячные доли.

Отдельная деталь, которая обосновывает наличие overlay: некоторые провайдеры
от стандарта отклоняются. У Adyen для CLP, CVE, IDR и ISK число десятичных
знаков отличается от ISO — например, ISK по стандарту имеет ноль знаков, но
для Adyen суммы подаются с двумя. Значит справочник покрывает почти всё, а на
отклонения нужен стандартный механизм переопределения.

### OpenAPI Overlay Specification 1.0.0 — формат переопределений

Проблема: часть требований в спеке не выражена структурой, и нужен файл, где
человек это дописывает. Риск — обвинение в привязке к конкретному провайдеру.

Решение: Overlay — официальная спецификация OpenAPI Initiative, проекта Linux
Foundation, опубликованная в версии 1.0.0 в октябре 2024. Определяет формат
документа, который дополняет существующее описание OpenAPI, оставаясь в
отдельном файле. Механически это список действий, адресующих элементы через
JSONPath, с операциями `update` и `remove`.

Среди официально заявленных сценариев — конфигурация для разных окружений
развёртывания, разделение ответственности для метаданных, и подстановка
параметров там, где они не были указаны явно. Ключевая формулировка
спецификации: механизм согласованных, детерминированных изменений описания
OpenAPI как средство автоматизации.

Экосистема уже использует Overlay для этой задачи: Fern рекомендует overlays
вместо собственных override-файлов именно из-за переносимости по экосистеме
OpenAPI, поддержка есть в Bump.sh.

Формулировка для защиты: это не самодельный костыль, это реализация открытого
стандарта.

### JSON Schema — условная обязательность полей

Проблема: «bank_code обязателен для type=sbp» написано в `description`, без
`oneOf` и `discriminator`.

Решение: `dependentRequired` требует наличия определённых свойств при наличии
заданного свойства, `if`/`then`/`else` применяют подсхему по результату другой
подсхемы. Доступность зависит от версии: OpenAPI 3.1 использует JSON Schema
2020-12 и поддерживает их нативно; OpenAPI 3.0 опирался на draft-07, но
запрещал `else`. Для этого случая в официальном реестре расширений OpenAPI
зарегистрированы `x-jsonschema-if` и `x-jsonschema-else`.

Три пути, все на стандартах:

| Вход | Как читаем |
|---|---|
| OpenAPI 3.1 | `dependentRequired`, `if/then/else` нативно |
| OpenAPI 3.0 с `x-jsonschema-*` | зарегистрированные расширения |
| OpenAPI 3.0 без них | Overlay дописывает `dependentRequired` плюс warning |

### Standard Webhooks — подпись уведомлений

Проблема: в спеке написано «HMAC-SHA256», но не задано, что подписывается и в
каком виде приходит подпись.

Решение: открытая спецификация с референсными реализациями для многих языков,
включая гем для Ruby, принятая OpenAI, Anthropic, Google Gemini, Kong, Svix,
Supabase, Vanta, Drata.

Задаёт три заголовка: `webhook-id` (уникальный идентификатор доставки),
`webhook-timestamp` (unix-время отправки), `webhook-signature`. Подписываемая
строка — конкатенация идентификатора, метки времени и тела через точки, затем
HMAC-SHA256 общим секретом; в заголовок пишется идентификатор алгоритма `v1`,
запятая, base64-хеш. Спецификация допускает и симметричные, и асимметричные
подписи. Метка времени попытки — мера защиты от replay-атак.

Наш верификатор параметризуемый с профилями: `standard_webhooks` по умолчанию,
`custom` для отклонений. NovaPay использует hex и raw body, что подтверждено
экспертами как канон для этого кейса.

Сравнение подписей константное по времени — эталонные реализации используют
constant-time comparison.

### Idempotency-Key — трактовка кода конфликта

Проблема: в спеке ответ с кодом конфликта на создание выплаты возвращает не
ошибку, а объект выплаты. Наивный генератор смапит любой 4xx в отказ.

Решение: черновик IETF `draft-ietf-httpapi-idempotency-key-header` в статусе
Standards Track описывает семантику явно. При повторном запросе, отправленном
после завершения оригинального, ресурс должен ответить результатом ранее
завершённой операции — успехом или ошибкой.

Значит это успешный путь дедупликации. Сгенерированный сервис подхватывает
существующую выплату.

Отсюда же следует детерминированный ключ идемпотентности от идентификатора
операции: случайный ключ не дедуплицирует повторы.

Бонус: черновик документирует реальные реализации в индустрии — BBVA Open
Platform использует собственный `X-Unique-Transaction-ID`, WebEngage
использует `x-request-id`. Готовый словарь алиасов.

## Отраслевой прецедент

ActiveMerchant — библиотека платёжной абстракции, извлечённая из Shopify.
Требование Shopify к простому и единому API для доступа к десяткам разных
платёжных шлюзов с очень разными внутренними API было главным принципом при
проектировании. В продакшене с июня 2006 года, поддерживается командами
Shopify и Spreedly, даёт стандартизованный интерфейс для authorize, capture,
purchase, refund и void, поддерживает Adyen, Authorize.Net, Braintree, PayPal,
Stripe, Worldpay.

Это наш кейс, решённый вручную двадцать лет назад. Открытая лицензия и Ruby,
поэтому изучаем как эталон устройства базового класса, объекта результата и
конвенций маппинга ошибок — тем более что настоящий `Provider::BaseService`
нам не предоставят.

## Как доказываем корректность

Три механизма, все машинные.

**Валидация против спеки.** Гемы `committee` и `openapi_first` проверяют
запросы и ответы на соответствие описанию OpenAPI. Мы прогоняем через них
запросы, которые формирует сгенерированный сервис, против исходной спеки.
Утверждение «мы правильно преобразуем данные» перестаёт быть словами.

**Покрытие спецификации.** У `openapi_first` есть механизм проверки, что всё
описание API покрыто при тестировании. Отсюда метрика для демонстрации: одна
цифра вида «спецификация покрыта на 87%, непокрытое перечислено в отчёте».

**Golden-тесты.** Один и тот же вход даёт байт-в-байт один и тот же выход,
зафиксированный в репозитории и проверяемый в CI. Это доказательство
детерминированности генератора, а значит отсутствия нейросети внутри. С LLM
такое доказательство невозможно.

## Границы: что мы не реализуем

Ретраи, очереди, шифрование секретов и алерты — инфраструктура Space Payments,
она уже существует. Наша задача — извлечь политику из спеки, выразить её
данными и сгенерировать вызов.

| Механизм | Что делаем |
|---|---|
| Ретраи и backoff | Извлекаем политику из кодов ответов и `Retry-After`, выражаем таблицей `RETRY_POLICY`. Механизм не реализуем |
| Очереди | Не трогаем. Методы синхронные и идемпотентные, планирование — вызывающей стороны |
| Шифрование секретов | Не реализуем. Генерируем чтение из `provider.credentials` |
| Алерты | Определяем, когда алертить (401, 500, нераспознанный код), генерируем вызов |
| Подпись вебхука | Реализуем честно — часть протокола провайдера |
| Ключ идемпотентности | Реализуем честно — часть протокола провайдера |

Ни в одном критерии оценки нет «реализована система ретраев». Есть
«обрабатывает ответы, статусы операций и ошибки» и «предусмотрена обработка
ошибок при разборе спецификации и генерации файлов» — второе про надёжность
генератора, и вот там усилия оправданы полностью.

## Допущения, требующие фиксации в документации

Эксперты подтвердили, что производственный класс и harness предоставлены не
будут, а допущения нужно описывать в `INTEGRATION.md`.

1. Контракт `Provider::BaseService` смоделирован по примеру из описания кейса.
2. `request_method` — логический тип действия, не HTTP-метод (подтверждено
   экспертами).
3. `operation.amount` в major units, провайдер ожидает minor units.
4. Канонический маппинг статусов взят из задания и подтверждён экспертами.
5. Для NovaPay канон: копейки, `bank_code` обязателен при `sbp`, подпись
   `HMAC-SHA256(raw body, secret)` в hex (подтверждено экспертами).

## Соответствие правилам

| Требование Положения | Как соблюдаем |
|---|---|
| 7.8.1 Без проприетарного ПО | Все зависимости с открытыми лицензиями, список в `DEPENDENCIES.md` |
| 7.8.2 Без проприетарных внешних API | Генератор не делает сетевых вызовов вообще |
| 7.8.3 Ruby более 50% | Ядро целиком на Ruby, веб-интерфейс тонкий на Rack и ERB без npm |
| 7.8.4 Без нейросетей | Только справочники, регулярки, метрики строк, эвристики по структуре. Детерминированность доказывается golden-тестами |
| 7.8.5 Отчёт по технологиям | `DEPENDENCIES.md` подготовлен заранее |

Запрет п. 7.8.4 касается функционирования прототипа, разработка кода с
помощью ИИ им не затрагивается.
