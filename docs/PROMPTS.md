# Промпты для Claude Code

Готовые промпты по порядку. У каждого есть **критерии приёмки** — ссылки на
идентификаторы из `docs/RUBRIC.md`. Не переходи к следующему промпту, пока
критерии текущего не выполняются на живом прогоне.

Не склеивай промпты. Агенты работают лучше, когда задача одна.

Перед началом: `CLAUDE.md` в корне, `.claude/agents/` на месте. Проверить —
команда `/agents`.

## Актуальный порядок после чекпоинта 2

Записано 5 сентября 2026 по ответам экспертов на встрече и в чате (дословно в
`docs/QUESTIONS.md`, следствия в `docs/ASSUMPTIONS.md`). Третий чекпоинт —
воскресенье 6 сентября, он же решающий.

Что сказали и что из этого следует:

- **«Важнее чужие OpenAPI-файлы уметь парсить и что-то из них доставать»,
  чем цикл `broken.yaml` → отчёт → `--fix`.** Промпт 11 уезжает в конец,
  промпт 10 становится единственным приоритетом.
- **«Было бы интересно на этот файлик посмотреть» и «репозиторий можете через
  куратора скидывать».** Эксперты будут читать сгенерированный сервис по чужой
  спецификации и наш код глазами. Значит качество читаемого важнее количества
  функций.
- **«Это достаточно последовательный, понятный процесс».** CLI больше не
  трогаем ради понятности — промпт 12 сокращается до пакетного режима.
- **«Вы это всё завернули в презентацию?»** На третьем чекпоинте показываем
  живой терминал, а не вывод, вставленный в слайд.
- **Контракт сузился** (ответы про `process_callback` и сохранение
  идентификатора) — это уже сделано, см. коммит «Контракт по ответам
  экспертов».

Порядок работ до третьего чекпоинта:

| Шаг | Что | Зачем именно сейчас | Где |
|---|---|---|---|
| 1 | Отправить куратору репозиторий, слайды и `output/` по чужой спеке | Прямая просьба экспертов на встрече | вне кода |
| 2 | Роли операций и статусы в справочниках: `cashout`, `approve`, `return`, статусы Adyen | 5 из 12 операций Adyen без роли, 41 из 79 статусов без пары; правится данными, не кодом — это и есть заявленная расширяемость | `rules/operations.yml`, `rules/statuses.yml` |
| 3 | Тело запроса по ролям для операций вне контракта | 81 из 97 полей тел не покрыто только потому, что payload собирается лишь для операции создания | `Service::Extras`, `Service::Payload` |
| 4 | Вторая цифра покрытия: «из того, что контракту вообще нужно» | Отвечает на вопрос «почему 34 %» честно, не подкручивая число | `Report::Coverage` |

| по остатку | Промпт 9 (сверка запросов со спекой), 11 (`--fix`), 8 (мок), веб-интерфейс | Бонусы, не критический путь | |

Записано 4 сентября 2026 по ответам экспертов (дословно в
`docs/QUESTIONS.md`, следствия в `docs/ASSUMPTIONS.md`). Второй чекпоинт —

Что изменилось:

- **Оценивают сгенерированный класс, а не живой трафик.** Промпт 8

## Промпт 6. Матчеры полей

```
Используй агента spec-analyst. Composite matcher по подходу COMA:

- NameMatcher: словарь → токенизация → расстояние Левенштейна
- TypeMatcher: type и format
- ConstraintMatcher: pattern, enum, minimum, maxLength
- StructureMatcher: путь в схеме, имя родителя

Агрегация с весами, порог 0.6. Порог решает не «присваивать ли роль», а
«попадёт ли решение в отчёт» (CLAUDE.md, «Что генерируем при неполной
спеке»; эксперты на чекпоинте 1: инструмент должен решать больше сам):
- выше порога — роль как heuristic с насчитанной уверенностью, без warning
- ниже порога, но хотя бы один матчер проголосовал — роль лучшего кандидата
  как heuristic с реальной уверенностью ПЛЮС warning field_role_low_confidence
  с баллами всех кандидатов; это пойдёт в evidence отчёта и в TODO кода
- ни одного голоса — роль не присваивается, warning field_role_unknown
- одна роль на два поля в одной схеме — конфликт: роль получает лучший,
  второй остаётся кандидатом с warning

Тесты обязательно включают:
- pattern ^7\d{10}$ определяет телефон при имени поля contact
- поле xref_tag_9, за которое никто не проголосовал, остаётся без роли и даёт
  warning; поле с баллом 0.4 получает роль-кандидата и warning с баллами
- amount и sum сопоставляются через словарь, а не метрикой строк
- обязательное поле без роли и необязательное без роли обрабатываются
  по-разному
- параметры (заголовки, path) получают роли так же, как поля тела
```

**Приёмка:** E3.1 (8 баллов), T3.2.

## Промпт 7. Генераторы

```
Используй агента codegen-engineer. Шаблоны, по одному, с проверкой после
каждого (генерация → ruby -c → rubocop → golden):

Правило поверх всего (эксперты, чекпоинт 1): генерация НЕ блокируется
никогда — файлы пишутся при любых предупреждениях; единственный отказ —
нечитаемая спека. Там, где IR не уверен, в код идёт лучший кандидат и TODO
с уверенностью и альтернативами, а не пустое место.

1. service.rb.erb. Обязательно:
   - четыре метода контракта, имена берутся из rules/contract.yml;
     HTTP-клиент вызывается как client.post(url, payload, headers) и
     client.get(url, headers) — так описали эксперты, больше не уточняем
   - payload запроса собирается по ролям полей; поле без роли — по правилу
     из CLAUDE.md «Что генерируем при неполной спеке»
   - STATUS_MAP, ERROR_MAP, RETRY_POLICY как замороженные хеши
   - ветка кода конфликта со схемой успеха (dedup) — по спеке, без акцента
   - ВСЕ события вебхука из enum плюс ветка неизвестного
   - константное сравнение подписи, обработка отсутствующего заголовка
   - детерминированный ключ идемпотентности (UUID v5 от operation.id)
   - пересчёт ограничений из спеки во внутренние единицы (profile.conditions
     + profile.units): минимальная сумма, длина external_id, паттерн
     телефона попадают в check_conditions
   - BASE_URL через ENV.fetch, таймауты конфигурируемы
   - TODO-заглушки в формате из инструкции агента, с уверенностью и
     списком кандидатов
2. INTEGRATION.md.erb. Девять разделов, потому что за это 5 баллов у экспертов
   и 5 у техжюри: авторизация и хранение секрета, ENV-переменные, таблица
   методов с идемпотентностью, маппинг статусов, обработка ошибок с
   действиями, конфиг ProviderGateway, схема подписи, "как подключить в
   приложение", "принятые допущения" (из docs/ASSUMPTIONS.md плюс
   допущения конкретного прогона)
3. fixtures.json.erb — примеры из examples спеки. Обязательно все три вида:
   запросы, ответы, уведомления (формулировка критерия требует именно всех
   трёх)
4. report.md.erb — сводка, покрытие, неоднозначности с готовыми
   overlay-фрагментами, unmapped-операции, противоречия в спеке

Детерминированность обязательна: никаких Time.now, rand, SecureRandom,
сортируй ключи перед выводом.
```

## Промпт 8. Мок-провайдер (бонус, по остатку времени)

Статус после чекпоинта 1: эксперты сказали, что «реальных запросов не будет,
результат — сгенерированный класс провайдера, в котором методы, поля и
хидеры соответствуют YAML». Живой трафик не оценивается. Мок остаётся
эффектной демонстрацией для отраслевого жюри (I1, I2) и делается ПОСЛЕ
промптов 10 и 12, если осталось время. Доказательство E2.1 переезжает в
промпт 9: сверка сформированных запросов со спекой.

```
Прочитай docs/IDEAS.md, идея 1. Реализуй генерацию мок-сервера провайдера из
той же спеки.

Требования:
- Rack-приложение из ERB-шаблона, поднимается командой ./mock-provider
- роутинг по путям из IR, ответы из examples спеки
- все объявленные коды ответов доступны через заголовок

Это демонстрация для жюри: сгенерированный сервис в живом обмене. Оценка

## Промпт 9. Тесты и валидация

```
Используй агента test-engineer. Эксперты на чекпоинте 1: «тесты нужны на
ваше решение, а не на сам сервис». Четыре уровня, все про генератор:

1. Юнит-тесты — добери покрытие
2. Golden-тесты на все спеки, побайтовое сравнение, обновление эталона только
   явной командой rake golden:update
3. Валидация сформированных запросов против исходной спеки через committee
   или openapi_first: загружаем сгенерированный сервис с фейковым client,
   вызываем create_request и fetch_status, перехватываем URL, заголовки и
   тело, валидируем против спеки. Это и есть доказательство «формирует
