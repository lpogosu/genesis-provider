# Принципы проекта

Правила, по которым устроен генератор. На этот документ ссылаются
комментарии в `lib/`, шапки справочников `rules/` и тексты отчётов, поэтому
заголовки разделов — якоря и не переименовываются. Как эти правила
воплощены в коде — `docs/ARCHITECTURE.md`; почему выбраны именно они —
`docs/CONCEPT.md`.

## Что мы строим

Инструмент, который принимает OpenAPI-спецификацию платёжного провайдера и
генерирует четыре артефакта: сервис по контракту `Provider::BaseService`,
документацию интеграции, фикстуры с примерами запросов, ответов и
уведомлений, отчёт о неоднозначностях и непокрытых элементах спецификации.

Это компилятор, а не интеграция с одним провайдером. NovaPay из описания
кейса — один тест-кейс из десяти в `spec/fixtures/specs/`.

## Три уровня доверия

Для каждого элемента спецификации идём по цепочке и останавливаемся на
первом успехе.

```
Уровень 1 — формальная структура спецификации
  required, enum, pattern, minimum/maximum, format, type, $ref,
  operationId, tags, securitySchemes, dependentRequired, if/then/else
  → используем молча, догадок нет

Уровень 2 — справочники и структурные эвристики
  ISO 4217, словари синонимов имён и статусов, роли эндпоинтов по
  комбинации (method + path + tag + operationId), порядок величин
  → используем, но помечаем в IR как heuristic с уверенностью

Уровень 3 — не вывелось или вывелось с низкой уверенностью
  → берём лучшего кандидата по словарям и эвристикам, даже ниже порога,
    и помечаем его: предупреждение в report.md, TODO с уверенностью и
    списком кандидатов в сгенерированном коде, слот в overlay
  → генерация не блокируется никогда; пустое место остаётся только
    когда кандидатов нет вообще
  → никогда не угадываем молча: грех — не догадка, а догадка без пометки
```

Молчаливая ошибка в платёжной интеграции хуже одного ручного шага: неверно
выведенный множитель суммы означает перевод в сто раз больше, а код при
этом выглядит корректным. Но пустое место — тоже ручной шаг. Эксперты
кейса сказали прямо: «инструмент должен больше решать сам… человек уже всё
равно всё будет смотреть, но после того, как всё сгенерировано». Поэтому
инструмент решает сам везде, где есть хоть один кандидат, а человеку
оставляет проверку по отчёту, а не заполнение пропусков.

Есть одно место, где инструмент осознанно не берёт лучшего кандидата.
Статус `PART_DONE` читался бы как `DONE`, то есть «выплачено», если снять
ведущее слово. Частично проведённый платёж, помеченный как выплаченный, —
запрещённое направление ошибки, поэтому вывода нет вовсе, а предупреждение
называет отвергнутого кандидата и объясняет отказ. Список таких слов —
секция `modifiers` в `rules/statuses.yml`.

Каждое выведенное значение в промежуточной модели — `IR::Derived` с полями
`source` (`structural`, `overlay`, `registry`, `heuristic`, `unknown`),
`confidence` и `evidence` — строкой обоснования, которую печатает отчёт.

## Роли вместо имён полей

Имён полей бесконечно много (`amount`, `sum`, `total`, `value`), ролей в
платёжной области шестнадцать:

`amount`, `currency`, `external_id`, `provider_operation_id`,
`recipient_type`, `recipient_phone`, `bank_code`, `bank_name`, `card_number`,
`status`, `error_code`, `error_message`, `created_at`, `completed_at`,
`idempotency_key`, `signature`.

Промежуточная модель хранит роли. Сопоставление «имя поля → роль» делает
отдельный слой матчеров по принципу composite matcher (COMA, Rahm &
Bernstein 2001): `NameMatcher` (словарь синонимов, токены, Левенштейн),
`TypeMatcher` (type, format), `ConstraintMatcher` (pattern, enum, minimum,
maxLength), `StructureMatcher` (путь в схеме, имя родителя, расположение
параметра). Матчеры голосуют, веса и порог лежат в `rules/roles.yml`.
Порог решает не «присваивать ли роль», а «попадёт ли решение в отчёт».

Роли операций: `create_payout`, `create_deposit`, `fetch_status`, `cancel`,
`confirm`, `refund`, `balance`, `webhook`, `unmapped`. На контракт
`Provider::BaseService` отображаются `create_payout`, `create_deposit`,
`fetch_status` и `webhook`; `cancel`, `confirm`, `refund` и `balance`
генерируются отдельными публичными методами и отмечаются в отчёте как «не
отображено на контракт». Внутренних статусов платформы три:
`in_progress`, `approved`, `rejected`.

Новый провайдер — новые строки в справочниках `rules/`, а не новый код.

## Контракт Provider::BaseService

Реального класса платформы нет: контракт смоделирован по примеру из
описания кейса и подтверждён экспертами как несущественный («базовый
класс-фабрика»). Это допущение записано в `docs/ASSUMPTIONS.md` и в разделе
«Принятые допущения» каждого сгенерированного `INTEGRATION.md`. Машинный
источник контракта — `rules/contract.yml`; в шаблоне сервиса и в `lib/`
нет ни одного литерала имени метода контракта.

Четыре метода:

```ruby
def check_conditions(operation, request_method)  # предпроверки
def create_request(operation, request_method = 'create')
def process_callback(payload)
def fetch_status(operation)
```

Что известно о платформе (ответы экспертов дословно — `docs/QUESTIONS.md`):

- HTTP-клиент вызывается как `client.post(url, payload, headers)` и
  `client.get(url, headers)`; ответ читается как `response.status` и
  `response.body`.
- `request_method` — логический тип действия (`payment_method` шлюза:
  `sbp`, `card`, …), не HTTP-метод.
- У объекта `operation` гарантированы `id`, `amount` (в мажорных единицах)
  и `payout_requisite` — JSONB-хеш, плюс `gateway`,
  `provider_operation_key`, `status` по необходимости. Плоских полей
  `recipient_phone`, `bank_code`, `card_number`, `currency` у операции нет.
  Реквизиты только из `payout_requisite`: у СБП это вложенный хеш
  (`payout_requisite.dig('sbp', 'phone')`), у карты — плоский ключ
  (`payout_requisite['card_number']`). Ключ верхнего уровня — это
  `request_method`, отсюда ветка `case request_method` в сборке реквизитов.
- `create_request` возвращает `success(result: { id: … })`: платформа
  берёт `payload.dig(:result, :id)`. У `fetch_status` и `process_callback`
  `result` не нужен — статус меняют хелперы `approve_operation` и
  `reject_operation`.
- Первый аргумент `failure` — код платформы в духе HTTP (`:bad_request`,
  `:unauthorized`, `:unprocessable_entity`, `:too_many_requests`,
  `:internal_server_error`, `:forbidden`); смысл отказа — второй аргумент,
  ключ локализации.
- `process_callback` получает уже разобранный JSON. Подпись по сырым байтам
  проверяет публичный `verify_webhook_signature(raw_body, headers)`, который
  зовёт маршрут вебхука до разбора тела.
- Валюта берётся из спецификации, а не у платформы.
- Реквизит, которого нет в таблице `requisites` в `rules/contract.yml`
  (IBAN, номер счёта), вслепую не генерируется: TODO и явное место маппинга
  в `INTEGRATION.md`. Это граница третьего уровня доверия: догадка о
  спецификации обязательна, догадка о платформе запрещена.

Канонический маппинг статусов из описания кейса: `pending` → `in_progress`,
`processing` → `in_progress`, `completed` → `approved`, `failed` →
`rejected`, `cancelled` → `rejected`. Для остальных — словарь синонимов
`rules/statuses.yml`, при неудаче предупреждение.

## Что генерируем при неполной спеке

- **Обязательное поле с неопознанной ролью** — включаем в payload с лучшим
  кандидатом: роль с наибольшим баллом матчеров, даже ниже порога; если
  баллов нет — значение `example` из спецификации; если нет и его — `nil`.
  Рядом TODO с типом, ограничениями и списком кандидатов с баллами.
- **Необязательное поле с неопознанной ролью** — пропускаем, одна строка в
  `report.md`.
- **Роль ниже порога матчеров** — присваиваем лучшему кандидату как
  `heuristic` с реальной уверенностью плюс предупреждение.
- **Эндпоинт вне контракта** (`GET /balance`, `POST /cancel`) — отдельный
  публичный метод плюс отметка в `report.md` «не отображено на контракт».
- **Необъявленный HTTP-код** (у `GET /payouts/{id}` нет 429 и 500) —
  достраиваем обработку по умолчанию, не падаем.
- **Код ошибки в примерах, но не в enum** — карта ошибок строится как
  объединение enum и кодов из примеров, расхождение попадает в `report.md`.

## Единицы суммы

Экспонента минорной единицы задана стандартом ISO 4217: RUB → 2, USD → 2,
JPY → 0, KWD → 3, CLF → 4. Множитель определяется по коду валюты из таблицы
`rules/currencies.yml`, а не по слову «копейках» в описании. Порядок вывода:

1. Явное значение в overlay (`x-specgen-amount-unit`) — высший приоритет.
2. `type: integer` + код валюты из ISO 4217 → минорные единицы.
3. `type: number` с дробным `example` → мажорные единицы.
4. Проверка на согласованность: `minimum: 100000` при экспоненте 2 — это
   1000 RUB, что должно совпадать с описанием. Расхождение — предупреждение.
5. Не вывелось — предупреждение и слот в overlay.

Некоторые провайдеры отклоняются от стандарта (у Adyen ISK с двумя знаками
вместо нуля), поэтому overlay обязателен как механизм, а таблица — как
умолчание.

## Провайдер-нейтральность lib/

В `lib/` нет ни слова `novapay`, ни `sbp`. Ядро работает с ролями и читает
справочники. Всё провайдер-специфичное живёт в `rules/` (данные) или в
overlay-файлах. Если возникает желание написать `if provider == 'novapay'`
— это сигнал добавить правило в справочник, а не ветку в код. Инвариант
проверяется в CI и тестом `spec/unit/specgen/neutrality_spec.rb`.

Исключение с оговоркой: `bank_code` — имя роли поля из списка выше, оно
встречается в `lib/specgen/ir/roles.rb` как элемент словаря ролей, а не как
знание о провайдере.

## Детерминированность

Один и тот же вход обязан давать байт-в-байт одинаковый выход. В
генерируемом контенте нет `Time.now`, `rand`, `SecureRandom` и порядка
обхода хешей, зависящего от вставки. Если нужна метка времени — она
берётся из `ENV['SPECGEN_TIMESTAMP']` с фиксированным умолчанием. Ключ
идемпотентности — UUID v5 от `operation.id` (RFC 4122 §4.3, `Digest::SHA1`).

На этом стоят golden-тесты: `spec/golden/` сравнивает четыре артефакта по
выданной спецификации с эталоном `spec/fixtures/golden/novapay/` побайтно,
а CI повторяет генерацию всех десяти спецификаций дважды и сверяет
`diff -r`. Эталон обновляется только явно:
`SPECGEN_UPDATE_GOLDEN=1 bundle exec rspec spec/golden`.

## Язык

Всё, что читает человек, — по-русски: комментарии в коде, сообщения CLI,
предупреждения и обоснования, документация, сгенерированные `INTEGRATION.md`
и `report.md`. Всё, что читает машина, — по-английски: идентификаторы,
YARD-теги, ключи YAML, названия стандартов. Термины переводятся по
`docs/GLOSSARY.md`.

Тексты для человека не пишутся строками в коде: они лежат в
`locales/<код>/<стадия>.yml` и читаются через `Texts.t('ключ', имя:
значение)`. Русский — по умолчанию, `--locale en` или `SPECGEN_LOCALE=en`
дают английский; новый язык — новый каталог, а не правка кода. Набор ключей
во всех локалях обязан совпадать, это проверяет
`spec/unit/specgen/texts_spec.rb`. Описания примеров в тестах остаются на
английском.

## Правила кода

- Один класс — один файл, путь соответствует пространству имён.
- Никаких методов длиннее 20 строк, никаких классов длиннее 150.
- Константы `.freeze`, никаких мутируемых глобалов.
- Ошибки — свои классы от одного корня `SpecGen::Error < StandardError`,
  никогда `raise "строка"`.
- Генератор никогда не падает со стектрейсом на пользовательском вводе:
  битый YAML, циклический `$ref`, отсутствующий `paths`, не-OpenAPI файл —
  всё это внятное сообщение с указанием файла и места (JSONPath).
- Каждый публичный метод ядра — с YARD-комментарием.
- Сгенерированный код обязан проходить `ruby -c` и RuboCop
  (`config/rubocop_generated.yml`).

Definition of done для любого изменения: `bundle exec rspec` и
`bundle exec rubocop` зелёные; `./integrate --all` проходит на всех
спецификациях каталога; сгенерированный `.rb` проходит `ruby -c`;
golden-тест проходит; в `lib/` нет провайдер-специфичных строк; `report.md`
содержит осмысленные предупреждения; новые зависимости записаны в
`DEPENDENCIES.md`.

## Правила хакатона

- **Никаких нейросетей внутри прототипа** (Положение, п. 7.8.4). В рантайме
  нет вызовов LLM, embedding-моделей и весов. Инструментарий — словари
  синонимов, таблицы стандартов, регулярные выражения, расстояние
  Левенштейна, стемминг по правилам, эвристики по структуре спецификации.
  Всё это старше нейросетей на два десятилетия (schema matching:
  Rahm & Bernstein 2001, Do & Rahm 2002).
- **Ruby больше 50 процентов** исходного кода команды. Доля считается по
  правилам GitHub Linguist (в языковую полоску идут только типы
  `programming` и `markup`; YAML и JSON — данные, Markdown — проза;
  сторонние зависимости, результат сборки и сгенерированный код не
  считаются). Замер — `ruby bin/ruby-share`. Веб-интерфейс — оболочка:
  разбор, анализ, генерация и отчёт только на Ruby, фронт показывает
  результат и загружает файл, ничего не вычисляя.
- **Только открытый исходный код.** Каждая зависимость с открытой
  лицензией записана в `DEPENDENCIES.md` (имя, версия, лицензия, зачем).
- **Никаких секретов** в репозитории и в сгенерированном коде: секреты
  только через `provider.credentials[...]` или `ENV.fetch`, в фикстурах
  только очевидные заглушки вида `test_api_key`, номера карт — только
  тестовые (`4111111111111111`).
