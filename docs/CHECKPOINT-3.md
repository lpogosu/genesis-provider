# Чекпоинт 3 — итоги встречи

Дата: 6 сентября 2026, решающая встреча. Формат: восемь минут. Слайды —
`docs/checkpoint-3/checkpoint-3.pdf` (три служебных слайда: показ шёл в
живом терминале и браузере).

## Что показали

Сгенерированный сервис по выданной спецификации, сверху вниз: ветка по
способу выплаты (`case request_method`), где условная обязательность
`bank_code` при `type=sbp` из прозы спецификации стала кодом с комментарием
об уверенности; `INTEGRATION.md` с переменными окружения, авторизацией и
таблицами; `report.md` с операциями, схемами, полями, предупреждениями и
покрытием. Веб-интерфейс: выбор спецификации из каталога или загрузка
файла, четыре артефакта с отрендеренным Markdown, список предупреждений.
Автотесты генератора.

## Вопросы экспертов и ответы

- «Столько комментариев — откуда они берутся? Через Ruby-код или какая-то
  нейросетевая штука?» — Комментарии заложены в ERB-шаблоны и презентеры
  генератора; нейросетей в инструменте нет. Ответ принят: «А, то есть уже в
  шаблоны это всё вставляется. Понял».
- «Вкратце, как это всё работает — парсеры, как шаблоны заполняются?» —
  Разбор спецификации в Ruby, промежуточная модель, международные стандарты
  (ISO 4217 для единиц суммы) и шаблоны. Подробно — `docs/ARCHITECTURE.md`.
- «В документацию добавили, как запустить ваш проект? README, что-нибудь
  такое?» — Да: README с запуском через Docker и без него, концепция, итоги
  чекпоинтов.
- «Сколько провайдеров пробовали? Не со всеми работает?» — Десять
  спецификаций, из них шесть чужих настоящих. Работает со всеми; у
  некоторых провайдеров есть статусы, не относящиеся к операциям выплаты
  (например, споры), их инструмент не сопоставляет и говорит об этом в
  отчёте. Ответ эксперта: «Бывает такое, что у операции статусы не только
  диспута. В любом случае хотя бы сопоставить основные».

## Как будут проверять

«Будем смотреть ваше решение на GitHub или GitLab и смотреть, как всё
работает». Репозиторий должен быть публичным: открыть его лучше за десять
минут до стоп-кода, и после стоп-кода коммитов быть не должно.

## Что изменили после встречи

- README переписан как пошаговая инструкция с ожидаемым выводом каждой
  команды; добавлен `docs/ARCHITECTURE.md` с диаграммами и описанием
  каждого файла.
- Сгенерированный класс теперь исполняется стадией проверки
  `Validators::ServiceCheck` на своих же фикстурах, итог печатается в
  консоли и в `report.md`.
- Команда `diff` сравнивает две версии спецификации через промежуточную
  модель.
- Заголовки `report.md` и `INTEGRATION.md` переведены на английский при
  `--locale en`.
- Примеры вывода по всем десяти спецификациям лежат в `examples/`.
